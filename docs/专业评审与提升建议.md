# 专业评审：宜必购盲盒系统 不足与提升建议（2026-08-17）

> 评审基线：需求规格说明书 V1.4 + V1.5 最终定稿（含 27 行补充）+ 当前实现（测试环境全绿）。
> 说明：文档功能点已全部实现；本评审从**安全/资金/并发/运营/工程化/合规**专业维度，
> 指出文档未覆盖或实现可增强之处。按 P0（安全资金风险）→ P3（优化）分级。

## P0：安全与资金风险（建议立即处理）

### 1. 顾客端"手机号即身份"无归属验证 ⚠️ 最大缺口
- **文档**：V1.5"用户唯一标识：手机号"；27 行"用户长按付款后回填实付"。
- **现状**：任意接口传手机号即视为该用户——**知道他人手机号即可抽奖、下单、抵扣、退款**，无短信验证码、无登录态。
- **建议**：①顾客端加**短信验证码登录**（首登绑定手机号，token 会话）；②或至少对敏感操作（退款、大额抵扣、改余额）加验证码二次确认。H5 无 App 推送，短信是最低成本通道。

### 2. 单日抵扣额度并发超限风险
- **文档**：V1.5 四重 min 含"单日上限−今日已累计"。
- **现状**：`remainingDailyQuota` 普通读 + `addQuota` upsert，**同一用户同门店并发两单**可同时读到相同剩余额度 → 双双通过 → **超单日上限**。
- **建议**：`daily_deduct_quota` 加**行锁**（SELECT ... FOR UPDATE）或唯一键 + 事务内重算；与中奖统计限额（已用行锁）保持一致。

### 3. 用户实付金额（paidAmount）无校验
- **文档**：27 行"用户填写刚刚实际付的金额提交，系统执行记账"（平台不碰资金，人工对账）。
- **现状**：paidAmount 仅记录，**不校验是否等于应付 payAmount**，也不与 payAmount 差异告警。
- **建议**：记录差异字段（paidDiff）+ 报表标识"实付≠应付"异常单，便于人工对账（不拦截，符合"不碰资金"）。

### 4. 商家收款码无审核
- **文档**：模式 A 商家上传自家收款码。
- **现状**：上传即生效，**无平台审核**——恶意商家可放置他人收款码骗取付款。
- **建议**：平台后台加收款码审核（待审/通过/驳回），审核前顾客端提示"收款码待审核"。

### 5. 测试确认支付接口无风控
- **文档**：微信支付（真实收商家年费）。
- **现状**：`renew-order/{no}/confirm` 为公开确认接口（测试用）——**生产若遗留，任何人可"确认支付"不付钱得会员**。
- **建议**：confirm 接口加**管理员开关**（仅 wx_pay_enabled=0 且平台后台显式开启测试模式时可用）；生产强制走微信回调。

## P1：业务完整性缺口

### 6. 个人身份二维码（长期）缺失
- **文档**：V1.5 第四章"用户个人身份二维码，长期有效，仅识别身份，用于退款"；三方式之一主推。
- **现状**：只做了**动态核销码**（2 分钟），**长期身份码未实现**。
- **建议**：个人中心生成长期身份码（含用户 ID 加密），商家扫后查该用户本店历史订单 → 选单退款（流程文档已定义）。

### 7. 商家本店订单无 Excel 导出
- **文档**：27 行"订单流水，支持导出 Excel，用于线下结算"。
- **现状**：订单列表有，**导出缺失**（仅余额流水/团购登记/宜必购对账可导出）。
- **建议**：merchant orders 加导出（复用 ReportService.toExcel）。

### 8. 模式 B 凭证二维码前端未渲染
- **文档**：模式 B 生成"一次性加密订单凭证二维码"。
- **现状**：顾客端显示 token 文本，**未渲染二维码图**（qrcode CDN 已在钱包动态码使用）。
- **建议**：order-b 返回后前端用 qrcode 渲染，商家扫码枪直接扫。

### 9. 券有效期 30 天写死
- **文档**：未指定有效期。
- **现状**：`COUPON_VALID_DAYS=30` 常量。
- **建议**：平台后台配置 `coupon_valid_days`（不写死，与 free_trial_days 同模式）。

### 10. 用户端无到期/返还触达通道
- **文档**：跨店返还"推用户手机弹窗"、V1.5 未提用户端提醒。
- **现状**：商家站内消息已做；**用户端无任何推送/消息通道**（H5 后台无法主动推）。
- **建议**：用户端消息表 + 打开 H5 时轮询展示（钱包页弹窗）；短信通道（P0-1 接入后复用）做返还/到期提醒。

### 11. 宜必购渠道与 V1.5 门店级抵扣关系未明确
- **文档**：V1.5 门店配置"门店之间隔离"；V1.4 宜必购用全局 rate。
- **现状**：宜必购仍用全局 balance_deduct_rate，**未纳入门店级/单日额度体系**。
- **建议**：明确宜必购抵扣规则（保留全局 or 按消费归属门店）；文档补一句即可，避免口径不一致。

## P2：运营与容灾

### 12. 微信支付回调无补单机制
- **现状**：回调失败（网络/验签异常）订单永久挂"待支付"，**无超时关闭/主动查单补单**。
- **建议**：定时任务轮询待支付订单 → 调微信查单 → 成功则确认（微信"查单"接口幂等）。

### 13. 平台敏感配置 DB 明文
- **现状**：wx_pay_api_key/v3_key 等 DB 明文（仅展示脱敏）。
- **建议**：**加密存储**（AES，密钥走环境变量/配置中心）；DB 泄露不泄密钥。

### 14. 无定时任务/异常监控告警
- **现状**：JobService 失败仅日志；GlobalExceptionHandler 已打日志但无告警。
- **建议**：失败告警（飞书/邮件 webhook）+ 关键指标（订单/退款/补单数）每日统计。

### 15. 流水与消息表无归档/清理
- **现状**：user_balance_flow 禁删（正确）；announce_log/merchant_message 无限增长。
- **建议**：announce/消息定期清理（保留 N 天）；流水按年归档分表（量大时）。

## P3：工程化与合规优化

### 16. 无单元测试/CI
- **现状**：10 个集成冒烟脚本（功能验证强），但**无单元测试、无 CI 流水线**。
- **建议**：核心计算（四重 min/有效期叠加/折扣率）补 JUnit 单测；GitHub Actions/本地脚本做构建+冒烟门禁。

### 17. Schema 演进靠幂等存储过程堆积
- **现状**：21 表 + 多次 ALTER 存储过程。
- **建议**：引入 **Flyway/Liquibase** 管理迁移（新表/字段走版本化 migration），替换手工幂等脚本。

### 18. 报表大数据量性能
- **现状**：报表 findAll + Java 过滤（数据量小可用）。
- **建议**：报表改 **SQL 聚合/分页**（索引：merchant_no+create_time 已有部分）；Excel 导出流式（SXSSF）防内存溢出。

### 19. 合规与审计细节
- **建议**：①隐私说明（手机号/消费数据收集用途）；②操作日志保留周期声明；③商家端敏感操作（上传收款码/改抵扣配置）也入审计日志（当前主要记录核销/退款/调整有效期）。

## 优先级建议落地顺序

| 批次 | 内容 |
|---|---|
| P0（1 轮） | ①短信验证码登录 ②单日额度行锁 ③paidAmount 差异标识 ④收款码审核 ⑤测试确认接口风控 |
| P1（2 轮） | ⑥长期身份二维码 ⑦订单导出 ⑧凭证码渲染 ⑨券有效期可配 ⑩用户端消息 ⑪宜必购口径 |
